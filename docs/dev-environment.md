# Development environment

Nothing is installed on the owner's laptop. All development, testing and staging work runs on the development server, in containers. The server's address and login are kept in the owner's private notes, not in this repository.

- Project copy: `/opt/mkt-dev/marketing`, synced from the laptop with `rsync` (without `node_modules`).
- Commands: `/opt/mkt-dev/run.sh "<command>"` runs the command in the `node:24.20.0` image (Node 24.20.0, npm 11.19.0), limited to 2 GB of memory and 1.5 CPUs. The script is `infra/dev/server-run.sh`.
- Database: the compose project `mkt-dev` (`infra/dev/compose.yaml`), PostgreSQL 17.11 by digest, bound to `127.0.0.1:54329` on the server only. Start it on the server with `docker compose -f infra/dev/compose.yaml up -d --wait`.
- Secret scanner: gitleaks 8.30.1 at `/opt/mkt-dev/bin/gitleaks`, checksum verified.
- Shared host: the server also runs Aztek staging and other projects, with little free memory. Keep containers capped and do not touch other projects' folders or containers.
- Checks: `/opt/mkt-dev/run.sh "npm ci && npm run verify"` passed on 2026-10-04 (63 tests passed, 1 skipped: the model check, which needs an API key).
- Browser checks: `npm run e2e` runs the Playwright suite in `apps/dashboard/e2e` (Chromium, desktop and phone projects) against a real stack it starts itself: a throw-away database, the core, a worker with the stand-in model, and the built dashboard. It is separate from `npm run verify`. The server runs it in a derived image, `mkt-dev-browser:1`, built once from `infra/dev/browser.Dockerfile` (the same Node image plus Chromium): `docker build -f infra/dev/browser.Dockerfile -t mkt-dev-browser:1 infra/dev`. Run it with `/opt/mkt-dev/server-run-browser.sh "npm ci && npm run e2e"` (script: `infra/dev/server-run-browser.sh`, installed beside `run.sh`; 3 GB of memory and 1.5 CPUs, the cap the owner accepted). The suite builds the dashboard and uses ports 3410 to 3412 on the host (`E2E_PORT` moves them); `E2E_REUSE_BUILD=1` skips the dashboard build on a rerun while specs are being written. CI runs it as the second job, `e2e`.
- Infrastructure tests: `node --test infra/prod/test/*.mjs` builds the production images (`infra/prod/Dockerfile`) and starts containers from them, so it needs Node and the Docker client together. The host has Docker but no Node, and nothing is installed on it, so the server runs these tests in a derived image, `mkt-dev-infra:1`, built once from `infra/dev/infra.Dockerfile` (the same Node image plus the Docker CLI 29.9.1 and buildx 0.38.0, both checked by sha256): `docker build -f infra/dev/infra.Dockerfile -t mkt-dev-infra:1 infra/dev`. Run them with `/opt/mkt-dev/server-run-infra.sh "node --test infra/prod/test/images.test.mjs"` (script: `infra/dev/server-run-infra.sh`, installed beside `run.sh`; 2 GB of memory and 1.5 CPUs, and gitleaks mounted read-only from `/opt/mkt-dev/bin`). The script mounts the host's Docker socket, which gives the container root-equivalent access to the whole host, including the other projects on it. It is for the development server and the owner's own sessions only; never use it in production or CI. The image builds run in the host's Docker, outside the 2 GB cap, one at a time. The tests tag their images `mkt-m7test-<target>:t39` and name every container `mkt-m7test-*`, removing the containers afterwards. CI runs them in the `e2e` job.
- Owner bootstrap: on the server, `BOOTSTRAP_DATABASE_URL=<a role that may write the tenancy tables> npm run bootstrap --workspace @mkt/core -- --owner-email <address>` creates the two brands and the platform owner and prints a temporary password once. See the plan, decision 11.
