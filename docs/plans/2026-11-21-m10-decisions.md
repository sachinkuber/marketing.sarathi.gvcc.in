# M10 Decisions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** After research, the owner answers a short tailored questionnaire, then confirms candidate verified facts and safety rules. An agent that cannot settle something asks the owner instead of guessing, and the owner's answer resumes its job. Research becomes safe for customers' brands, and it digs deeper.

**Architecture:** Two new agents on the Phase 1 work engine:
- `questionnaire` turns the draft profile's gaps into 20 to 30 questions with suggested answers;
- `facts_rules` turns the accepted profile, the answers and the documents' extracts into candidate facts and safety rules.

Both run with no web tools. Their results become owner decisions through M8's suggestion service (facts and rules) and the M8 `questionnaire`, `question` and `answer` tables (questions).

A new engine path lets any agent job end in `waiting_for_answer`: the worker raises an `agent_question` through a core worker route, and the owner's answer re-queues the job as a new attempt that sees the answer.

Research gains three checks:
- a source address check against the URLs the provider actually returned;
- a runtime search cap per run;
- deeper prompts.

The PDF split moves into a child process.

**Tech Stack:** Node 24.20.0 running TypeScript directly, Express 5, PostgreSQL 17 with row-level security, node-pg-migrate SQL migrations, pg-boss, zod, vitest, Playwright, Next.js (dashboard), the pinned Anthropic SDK.

**Spec:** `docs/specs/2026-11-20-phase-2-onboarding-strategy.md` (approved version 1). This plan covers:
- sections 4 (steps 4 to 7), 5, 6 (`questionnaire`, `facts_rules`), 7, 8.2, 9, 11 and 12 (questionnaire, facts and rules, agent questions);
- packages 25, 26 and 27 of section 16;
- the M9 items marked "deferred to milestone 10" in `docs/progress.md`;
- the lessons of the first live research run on 2026-11-21.

Phase 1 rules in `docs/specs/2026-10-04-phase-1-foundation.md` still hold.

## Global Constraints

- **Where commands run.**
  - Commands run on the development server only.
  - `rsync` the tree to `/opt/mkt-dev/marketing`, excluding `secret-keys`, `2fa`, `node_modules`, `.superpowers` and `.next`. Then run `ssh root@<dev-server> '/opt/mkt-dev/run.sh "timeout <s> <command>"'`.
  - Before an rsync, `pgrep -fa "[v]itest run|[p]laywright"` on the server must print nothing.
  - Nothing runs on the laptop but git and editors, and that includes prettier.
  - No server address goes in any file or commit. Wrap every server command in `timeout`.
- **Dependencies.** No new runtime dependency. Every dependency stays pinned exactly (`npm run check:pins`).
- **Migrations.**
  - Files are `packages/db/migrations/NNNN_name.sql`; the next number is `0028`. Each has `-- Up Migration` and `-- Down Migration`.
  - A down migration never deletes the owner's rows.
  - Brand-scoped tables follow M8's rules: RLS forced, a single `brand_isolation` policy, composite brand foreign keys, `mkt_app` grants, `select` for `mkt_readonly`.
- **Worker boundary.** The worker never imports `@mkt/db`, `pg` or core code. It reaches data only through core's worker routes with the attempt token.
- **Untrusted input.** These are all untrusted (AI-6):
  - web pages, search results, documents and their extracts;
  - profile values that came from them;
  - the owner's free-text answers.

  They reach the model wrapped with `wrapData` (`packages/shared/src/summary.ts`) and labelled as data, and they are never followed as instructions.
- **New agents.**
  - `questionnaire` and `facts_rules` run on `claude-sonnet-5-5`, job class `production`, `effort: 'medium'`, `maxTokens: 16000` and no tools.
  - Each sends its output schema as structured output.
  - Result types are `questionnaire.v1` and `facts_rules.v1`.
- **Questionnaire.** Questions are mostly multiple choice. Each has a suggested answer, `why` it is asked, and the key it is about. Exact limits are in Task 3.
- **Facts and rules.**
  - Every candidate fact and every candidate rule cites at least one source id from the job's input.
  - A fact carries a review date in `YYYY-MM-DD`.
  - Rule kinds are exactly M8's: `forbidden_topic`, `forbidden_claim`, `forbidden_word`, `competitor_not_named`, `tone_limit`, `pause_dates`.
  - A fact or rule exists only after the owner's decision (spec 7; test 43). Accepting a fact still needs a qualifying source, or the owner's own wording (M8 `writeFact`).
- **Owner statements (D7).** Every owner answer that becomes a source is a `research_source` with:
  - kind `owner_statement` and result `stated`;
  - `stated_by`, the user;
  - `read_at`, when it was stated;
  - the exact wording as `extract`, with no cut.
- **Agent questions (spec 9).**
  - A job has at most one open question.
  - While a question is open, the job's state is `waiting_for_answer`: not failed, not dead, not running. Its run stays running.
  - The answer starts a new attempt of the same job.
  - An unanswered question is reminded every 72 hours. It never times out into a guess.
- **Research caps.** These are unchanged: 20 searches and 30 fetches per job, and 150 searches per research run for a brand. From this milestone the per-run cap is enforced while the run is going (Task 10).
- **Permissions.** Every onboarding route and screen uses permission `onboard_brand` (platform owner only).
- **Audit actions** follow `<domain>.<snake_case_event>`. Detail carries ids, counts and keys only, never answer, fact or rule text.
- **Copy.** Dashboard and API errors use plain words and no apologies. An error says what is wrong and how to fix it. Screens work at 390 x 844 with touch.

## Review Focus

- **The owner answers half the questionnaire, leaves, and comes back the next day.** Every typed answer is still there. "Finish" works with questions left blank, and the blank ones are simply not passed on. Task 6 test: `answers save as typed and a half-answered questionnaire can be finished`.
- **The owner answers an agent question after the job was cancelled or the agent was switched off.**
  - For a cancelled job, the answer is refused with 409 `job_not_waiting` and nothing is re-queued.
  - For a switched-off agent, the job is re-queued and then held by the switch.

  Task 2 test: `an answer to a cancelled job's question is refused`.
- **A double click on "Send answer" or "Finish questionnaire".** The second request gets 409 (`already_answered`, `questionnaire_finished`). Exactly one job is re-queued, and exactly one set of owner statements is written. Tests in Task 2 and Task 6.
- **The worker dies after raising a question but before completing its queue row.** The queue's retry starts no attempt and raises no second question. Task 2 test: `a retried queue row of a waiting job starts no attempt`.
- **A facts result citing a source of another brand, or a fact resting only on a competitor page.**
  - Another brand's source: the result is refused with 422 `unknown_source`.
  - A competitor-only fact: it is stored as a suggestion that cannot be accepted as it stands (M8 `fact_needs_source`); the owner must edit it into their own words.

  Task 7 test: `facts that cite another brand's source are refused; a competitor-only fact cannot be accepted`.

- Test: `apps/core/test/agent-questions.test.ts`, `apps/worker/test/runner.test.ts`

**Interfaces:**
- **Worker route `POST /worker/jobs/:jobId/question`** (attempt token, `requireCurrentAttempt`):
  - Body (strict): `{ question: string ≤ 500, why: string ≤ 300, options: string[] (0–5, each ≤ 200), suggested: string ≤ 500 | null }`.
  - In one transaction, it inserts the `agent_question` (the job's brand, run and job) and ends the attempt with reason `waiting_for_answer` (`endAttempt`).
  - It queues a notification of kind `agent_question` (subject `{ kind: 'job', id: jobId }`) to each platform owner.
  - It audits `onboarding.agent_question_raised { questionId, jobId }` and returns 201 `{ questionId }`.
  - A second open question for the job gets 409 `question_open`.
- **`startAttempt`:**
  - A job with an open question returns `{ finished: false, outcome: 'waiting_for_answer' }` and starts no attempt. That is the core's side of "a retried queue row starts no attempt".
  - Otherwise the reply gains `answers: { question: string; why: string; options: string[]; answer: string }[]`: the job's answered questions, oldest first.
- **Worker:**
  - `JobContext.answers` is that list.
  - `JobContext.ask(q: { question; why; options; suggested }): Promise<never>` posts the question and throws `JobWaiting`.
  - `runJob` treats `JobWaiting` like a normal end without a result. It posts nothing, returns, and lets the queue row complete.
  - `runJob` returns without work for the `'waiting_for_answer'` outcome.
  - `CoreClient.raiseQuestion(jobId, token, body): Promise<{ questionId: string }>`.
- **Owner routes** (permission `onboard_brand`):
  - `GET /brands/:brandId/onboarding/agent-questions` returns `{ questions: { id, jobId, runId, agent, question, why, options, suggested, createdAt, answer, answeredAt }[] }`, open first, then the 20 newest answered.
  - `POST /brands/:brandId/onboarding/agent-questions/:questionId/answer`, body `{ answer: string 1..2000 }` (trimmed), does all of this in one transaction:
    - (1) locks the question;
    - (2) checks the job is neither cancelled nor dead nor finished, else 409 `job_not_waiting`;
    - (3) sets `answer`, `answered_by` and `answered_at`;
    - (4) inserts an owner-statement source with the exact answer, `stated_by` set, and links it as `source_id`;
    - (5) re-queues the job with `deps.queue.requeue(jobClass, jobId, currentQueueId)`, the call `requeueJob` uses;
    - (6) audits `onboarding.agent_question_answered { questionId, jobId }`.
  - It returns 200 `{ questionId, requeued: true }`. A second answer gets 409 `already_answered`.
- **Reminders:** `remindAgentQuestions(client, now): Promise<number>` runs from the approvals tick.
  - For every open question where `coalesce(reminded_at, created_at) < now − 72 h`, it queues `agent_question_reminder` to each platform owner and sets `reminded_at = now`.
  - Its count is added to the tick's reply, for example as a new `agentQuestionsReminded` field.
- **Job state helper** in `agent-questions.ts`:
  - `jobState(row: { finished: boolean; dead: boolean; cancelled: boolean; attempts: number; openQuestion: boolean }): 'waiting' | 'running' | 'waiting_for_answer' | 'done' | 'failed'`.
  - It returns `waiting_for_answer` when `openQuestion` and the job is not finished, dead or cancelled.
  - Task 8's research overview uses it (`apps/core/src/onboarding/research.ts` `stateOf`), and so do Tasks 6 and 7.

**Files:**

**Interfaces:**
- **`QUESTION_KEYS`:** `PROFILE_KEYS` plus `goals`, `priority_audiences`, `proof_points`, `never_say`, `competitors_not_named`, `tone_limits`, `pause_dates`, `capacity`, `success_measures`.
- **`questionnaireInputSchema`:**
  ```
  { brandName: string,
    profile: { key: ProfileKey, value: string, status: 'found'|'assumed'|'unknown' }[],
    open: { key: ProfileKey, proposed: string, confidence }[],
    gaps: { key: ProfileKey, why: string }[],
    unreadable: { kind, address: string | null }[],
    competitors: { name: string, website: string | null }[] }
  ```
  - `profile` is the current accepted items.
  - `open` is undecided or rejected profile suggestions.
  - `gaps` comes from the merge's outcome.
  - `unreadable` is the research sources whose result is not `read`.
- **`questionnaireResultSchema`** (`questionnaire.v1`, strict):
  ```
  { questions: { key: QuestionKey, text ≤ 300, why ≤ 300,
                 options: string[] (0 or 2–6, each ≤ 200), suggestedAnswer: string ≤ 500 | null }[] }
  ```
  - There are 10 to 30 questions. Each key appears at most once. The prompt aims for 20 to 30, as spec 6 says. The schema allows 10, so a brand whose research settled most of its profile, as Aztek's did, is not padded with filler questions or failed for having few gaps.
  - When `options` is not empty, `suggestedAnswer` is one of them, or null.
  - There is no `decision` field.
- **`agentQuestionSchema`** (shared by every agent that may ask):
  ```
  { question: { text ≤ 500, why ≤ 300, options: string[] (0–5), suggested: string | null } }
  ```
  Each agent's reply schema is `z.union([resultSchema, agentQuestionSchema])`. The provider schema is the `anyOf` of both, generated with `z.toJSONSchema` and stored in `output.schema.json`, as M9 does.
- **Definition:** as in Global Constraints, `resultType: 'questionnaire.v1'`.
- **Builder:** `buildQuestionnaireRequest(agent: LoadedAgent, input: QuestionnaireInput, answers: JobContext['answers']): ModelRequest`. It wraps every profile value, proposal, gap reason and competitor name with `wrapData`. When there are earlier answers to agent questions, they are added as `<owner_answer>` data.
- **Prompt rules (`system.md`):**
  - Ask first about the gaps, the assumed items and the unreadable sources, then about the strategy inputs in `QUESTION_KEYS` the profile does not settle. Aim for 20 to 30 questions.
  - Never ask what the profile already settles as `found`.
  - Prefer multiple choice, pre-filling the most likely answer from the profile.
  - `never_say`, `competitors_not_named`, `tone_limits` and `pause_dates` are always asked, because they feed the safety rules.
  - If the input is too thin to ask anything useful, raise an agent question instead.

**Interfaces:**
- **`factsRulesInputSchema`:**
  ```
  { today: 'YYYY-MM-DD', brandName: string,
    sources: { id: uuid, kind: SourceKind, address: string | null, documentName: string | null, extract: string }[],
    profile: { key: ProfileKey, value: string, status, sourceIds: uuid[] }[],
    answers: { key: QuestionKey, question: string, answer: string, sourceId: uuid }[] }
  ```
  `sources` holds every source the profile items and answers cite, plus the brand's document sources.
- **`factsRulesResultSchema`** (`facts_rules.v1`, strict):
  ```
  { facts: { statement ≤ 300, why ≤ 300, sourceIds: uuid[] (≥ 1), reviewDate: 'YYYY-MM-DD' }[] (≤ 40),
    rules: { kind: SafetyRuleKind, text ≤ 300, why ≤ 300, sourceIds: uuid[] (≥ 1) }[] (≤ 30) }
  ```
  - Every `sourceId` is one of `input.sources`; this is a refinement in the result handler (Task 7), because the schema cannot see the input.
  - A `reviewDate` is after `today`.
  - There is no `decision` field.
  - The reply schema is `z.union([factsRulesResultSchema, agentQuestionSchema])`.
- **Builder:** `buildFactsRulesRequest(agent, input, answers): ModelRequest`. It wraps every extract, profile value and answer with `wrapData`, carrying the source id as an attribute.
- **Prompt rules:**
  - A fact is one checkable statement the brand can make about itself: what it sells, where, since when, how many, which warranty, which certification with its issuer. It cites the sources that state it.
  - A fact never rests only on `competitor`, `search` or `social` sources. If that is all there is, leave it out, or ask.
  - Review dates are 3 months ahead for prices and offers, and 12 months ahead otherwise.
  - Rules come from the owner's answers to `never_say`, `competitors_not_named`, `tone_limits` and `pause_dates`, and from documents, and cite those answers.
  - When the owner's answers contradict each other, or contradict the brand's own site on something a fact or rule depends on, raise an agent question rather than pick one.

### Task 6: Core questionnaire: start, results, answers that save as typed, finish

**Files:**
- Create: `apps/core/src/onboarding/questionnaire.ts`, `apps/core/test/questionnaire.test.ts`

**Interfaces:**
