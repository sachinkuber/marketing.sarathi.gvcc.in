# M11 Strategy and gate 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** After the owner confirms facts and rules, two new agents finish onboarding: `brief_choices` lays out the open strategic choices, each with two or three options and a recommendation, and `strategist` writes the strategy brief from the owner's picks. The brief is a `strategy_brief` content item approved in the inbox. The owner can ask for changes, and a change to a fact the brief cites cancels its approval. An approved brief is gate 1 for the brand.

**Architecture:**
- Both agents follow milestone 10's decision-agent pattern exactly (`questionnaire`, `facts_rules`): an agent folder, shared zod schemas, a worker handler, an evaluation runner, a core start route and a result handler.
- Choices become M8 suggestions with step `choice`. The brief becomes a Phase 1 content version (`cv1` hash), moved straight to `awaiting_approval` after a fact check.
- "Ask for changes" adds Phase 1's unused `changes_requested` decision, with a handler per content kind.
- Invalidation uses Phase 1's unused `invalidated` state and the `approval_invalidation` table.
- The milestone also adds "add as a case" (C8), a research prompt fix from the 2026-11-22 live run, the cheap parked items, and the full browser journey (test 42).

**Tech Stack:** Node 24.20.0 running TypeScript directly, Express 5, PostgreSQL 17 with row-level security, node-pg-migrate SQL migrations, pg-boss, zod, vitest, Playwright, Next.js (dashboard), the pinned Anthropic SDK.

**Spec:** `docs/specs/2026-11-20-phase-2-onboarding-strategy.md`. This plan covers:
- sections 4 (steps 8 to 11), 5, 6 (`brief_choices`, `strategist`), 10, 11 ("add as a case") and 12 (brief choices, strategy brief);

Phase 1 rules in `docs/specs/2026-10-04-phase-1-foundation.md` and the app flow's section 5.6 (`docs/app-flow/2026-10-04-app-flow.md`) still hold.

## Global Constraints

- **Where commands run.**
  - Commands run on the development server only.
  - `rsync` the tree to `/opt/mkt-dev/marketing`, excluding `secret-keys`, `2fa`, `node_modules`, `.superpowers` and `.next`. Then run `ssh root@<dev-server> '/opt/mkt-dev/run.sh "timeout <s> <command>"'`.
  - Before an rsync, `pgrep -fa "[v]itest run|[p]laywright"` on the server must print nothing.
  - Nothing runs on the laptop but git and editors, and that includes prettier. If prettier rewrites a file on the server, copy it back with `scp` before committing.
  - No server address goes in any file or commit. Wrap every server command in `timeout`.
- **Dependencies.** No new runtime dependency. Every dependency stays pinned exactly (`npm run check:pins`).
- **Migrations.**
  - Files are `packages/db/migrations/NNNN_name.sql`; the next number is `0031`. Each has `-- Up Migration` and `-- Down Migration`.
  - A down migration never deletes the owner's rows.
  - Never alter an enum. Use the existing patterns: reference rows, checks, definer functions.
- **Worker boundary.** The worker never imports `@mkt/db`, `pg` or core code. It reaches data only through core's worker routes with the attempt token.
- **Untrusted input (AI-6).** These are all untrusted:
  - profile values, fact statements, rule texts;
  - the owner's free-text answers and picks;
  - an approver's change comment.

  They reach the model wrapped with `wrapData` (`packages/shared/src/summary.ts`) and labelled as data, and they are never followed as instructions.
- **New agents.**
  - `brief_choices` and `strategist` run on `claude-sonnet-5-5`, job class `production`, `effort: 'medium'`, `maxTokens: 16000` and no tools, as `questionnaire` does.
  - Each sends its output schema as structured output with no root `anyOf` (R7). The reply is one strict object with `ask: Ask | null`.
  - The result types are `brief_choices.v1` and `strategy_brief.v1`.
  - The first line of each request is fixed, so the e2e stand-in model can tell them apart:
    - `brief_choices`: `Find the open strategic choices.`
    - `strategist`: `Write the strategy brief.`
- **Facts in the brief (spec 10).**
  - Every fact the brief relies on is cited by id. When a result arrives, a cited id that is not an active fact of the brand refuses it (test 49).
  - A citation is `{ fact_id, text_hash: 'sha256:' + verified_fact.fact_hash }`.
  - A citation is **current** while the brand has an active fact whose `'sha256:' || fact_hash` equals its `text_hash`. So a review-date-only replacement keeps the brief valid, and a change of wording or a retirement does not.
- **Who decides on a brief.** Only a holder of `onboard_brand` (the platform owner) may approve, reject or ask for changes on a `strategy_brief` version. It is never approved in bulk (app flow 5.6).
- **Permissions.** Every new onboarding route uses `onboard_brand`.
- **Audit actions** follow `<domain>.<snake_case_event>`. Detail carries ids, counts, keys and revision numbers only, never brief text, comments, answers or fact text.
- **Copy.** Dashboard and API errors use plain words and no apologies. An error says what is wrong and how to fix it. Screens work at 390 x 844 with touch.
- **Agent version numbers.** A changed agent folder needs a higher `version` when that version number was already released on production. `research` is at 2 on production, so its change in Task 11 makes it 3. `brief_choices` and `strategist` start at 1.

## Review Focus

- **The owner asks for changes on the brief four times.**
  - The first three asks each start the strategist with the comment, and a new version arrives.
  - The fourth records the comment and closes the version, but starts nothing (the revision limit, app flow 5.6 point 7). The overview says the brief needs the owner's decision.

  Task 7 test: `after three revisions an ask for changes starts no new run`.
- **A fact the approved brief cites is replaced with new wording, or retired.** The approved version moves to `invalidated`, the owner is notified, and the overview shows "brief needs re-approval" with gate 1 off. A review-date-only replacement changes nothing. Task 7 tests: `rewording a cited fact invalidates the approved brief` and `a date-only replacement keeps the brief approved`.
- **A brief waiting for approval cites a fact that is then retired.** The waiting version is invalidated too, so it can no longer be approved, and the approve route answers 409 `not_awaiting_approval`. Task 7 test: `retiring a fact cited by a waiting brief invalidates it`.
- **A brand admin (not the platform owner) opens the brief in the inbox.**
  - Approve, reject and ask for changes all answer 403.
  - The item screen shows the brief read-only, with no decision buttons.

  Tests in Task 6 (`a brand admin cannot decide on a strategy brief`) and Task 10.
- **The strategist's result cites a fact id that is not in its input, or one retired since the job started.** It is refused with 422 `unknown_fact` (core), and the worker already refuses an id outside the input (`DecisionReplyInvalid`). No content version is created. Task 6 test: `a brief citing an unknown or inactive fact is refused`.

### Task 2: Shared schemas for brief choices and the strategy brief

**Files:**
- Create:

**Interfaces** (use `shown(max)` for text the owner reads and `given(max)` for input text, as `questionnaire.ts` does):
- **`CHOICE_KEYS`** = `['lead_audience', 'positioning_angle', 'first_channels', 'content_focus', 'posting_rhythm', 'goal_focus'] as const`.
- **`BASELINE_NEEDED = 'baseline needed (B1)'`**.
- **`briefChoicesInputSchema`:**
  ```
  strictObject {
    brandName: given(200),
    profile:  [{ key: PROFILE_KEYS, value: given(2000), status: 'found'|'assumed'|'unknown' }] (max 40),
    facts:    [{ id: uuid, statement: given(1000) }] (min 1, max 60),
    rules:    [{ kind: SAFETY_RULE_KINDS, text: given(1000) }] (max 60),
    answers:  [{ key: QUESTION_KEYS, question: given(300), answer: given(2000) }] (max 30)
  }
  ```
- **`briefChoicesResultSchema`:**
  ```
  strictObject {
    choices: [{ key: CHOICE_KEYS, question: shown(300), why: shown(300),
                options: [{ value: shown(200), tradeOff: shown(300), recommended: boolean }] (min 2, max 3) }] (max 6),
    ask: askSchema.nullable()
  }
  ```
  Its `superRefine` requires:
  - a result that asks holds no choices; otherwise 3 to 6 choices;
  - keys unique;
  - exactly one `recommended` option per choice;
  - option values unique within a choice (compared trimmed, without regard to case).
- **`strategistInputSchema`** = `briefChoicesInputSchema` extended with:
  ```
  today: z.iso.date(),
  picks: [{ key: CHOICE_KEYS, question: given(300), picked: given(300), notTaken: given(300)[] (max 2) }] (min 1, max 6),
  baseline: given(2000).nullable(),
  changeRequest: strictObject { comment: given(2000), previous: given(30000) }.nullable()
  ```
- **`strategyBriefResultSchema`:**
  ```
  strictObject {
    brief: strictObject {
      positioning: { statement: shown(200), paragraph: shown(1200) },
      audiences:   [{ name: shown(120), needs: shown(400), message: shown(400), where: shown(300) }] (1..5),
      themes:      [{ name: shown(120), why: shown(300), topics: shown(200)[] (2..6) }] (4..6),
      channels:    [{ channel: shown(80), audiences: shown(120)[] (1..5), why: shown(300) }] (1..8),
      cadence:     [{ channel: shown(80), postsPerWeek: z.int().min(0).max(21) }] (1..8),
      goals:       [{ metric: shown(120), from: shown(80), to: shown(80) }] (1..6),
      choicesMade: [{ key: CHOICE_KEYS, picked: shown(300), notTaken: shown(300)[] (max 2) }] (max 6),
      factIds:     uuid[] (min 1, max 40, unique)
    }.nullable(),
    ask: askSchema.nullable()
  }
  ```
  Its `superRefine` requires exactly one of `brief` and `ask` to be non-null.
- **`strategyBriefAgainstInput(result, input): { path: string; message: string }[]`**. Each of these is one error:
  - a `factIds` entry not in `input.facts`;
  - a `choicesMade.key` not in `input.picks`;
  - a goal `from` that is not `BASELINE_NEEDED` while `input.baseline` is null.
- **`strategyBriefPayload(brief, ctx: { brandId, contentItemId, brandName, facts: { id, statement, factHash }[] }): ContentPayload`**. It is pure and deterministic:
  - `kind` `strategy_brief`, `language` `en`, `title` `Strategy brief: ${brandName}`, `summary` = `positioning.statement`.
  - `body`, in this order:
    1. heading level 2 "Positioning", then a paragraph.
    2. heading level 2 "Audiences"; for each audience, a heading level 3 with its name, then an unordered list of "Needs: …", "Tell them: …" and "Where: …".
    3. heading level 2 "Content themes"; for each theme, a heading level 3 with its name, a paragraph with its why, then a list of its topics.
    4. heading level 2 "Channels", then a list of `${channel}: ${audiences.join(', ')}. ${why}`.
    5. heading level 2 "Plan: posts per week", then a list of `${channel}: ${n} a week`.
    6. heading level 2 "90-day goals", then a list of `${metric}: from ${from} to ${to}`.
    7. heading level 2 "Choices made", then a list of `${picked}` or `${picked} (not taken: ${notTaken.join('; ')})`. This section is left out when there are no choices.
    8. heading level 2 "Facts used", then a list of the cited facts' statements, in `factIds` order.
  - `fact_refs` = `factIds.map(id => ({ fact_id: id, text_hash: 'sha256:' + factHash }))`.
  - An id with no entry in `ctx.facts` throws.
