# Milestone 7 — Ship Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The product runs at `https://marketing.sarathi.gvcc.in` on the shared server in capped containers behind the existing proxy. A daily encrypted backup leaves the server and has been restored into a clean database. Failures reach the owner through the error tracker, the uptime checker and the alert path. The load test passes without slowing n8n. All 41 acceptance tests run together for gate 0 (packages 16, 17 and 18; tests 39 for images and logs, 40, 41, and the full run).

**Architecture:** One multi-stage `infra/prod/Dockerfile` builds four images from the same pinned Node base: `core`, `worker`, `dashboard` (Next.js standalone) and `ops` (migrations, queue install, bootstrap, backup and restore tools). Node runs the TypeScript sources directly, as it does today. `infra/prod/compose.yaml` runs core, worker, dashboard and Postgres with per-container processor and memory limits on three networks (`app`, `worker`, `data`), the zones spec 16 names. Configuration comes from root-owned `0600` env files outside the repository. The server's existing proxy routes `/api/` to the core and everything else to the dashboard. Backups run as a one-shot `ops` container on a host timer. Monitoring needs only one new piece of code: a worker heartbeat the uptime checker can read. The rest is wiring of what milestones 4 to 6 built.

**Tech Stack:** As pinned in spec section 3: Node 24.20.0, PostgreSQL 17.11 (same digest as tests), Next.js 16.3.4 (16.3.8 if decision 9 is accepted), Docker with the Compose plugin (version recorded at server inspection), the server's existing proxy, `@sentry/node` 10.73.0 (already pinned in `packages/stack-check`). New tools, each proposed below: `age` for backup encryption, `rclone` for the off-server copy, and an S3 client for the write-once audit store. Every command runs on the development server through `/opt/mkt-dev/run.sh`, or on the production host as stated.

**Spec:** `docs/specs/2026-10-04-phase-1-foundation.md` sections 1, 3, 4, 12, 14, 16, 17 (tests 38 to 41 and the whole table), 18 (packages 16 to 18), 19 (risk 3). Also `docs/progress.md`: every "Deployment precondition" and "Follow-ups" line in milestones 2b, 2c, 3, 4, 5 and 6 (listed per task below), and `docs/sachin-to-provide.md` section 1.

## Decisions proposed to the owner

Each one is the rule the build will follow. Recommended: accept all of them, except where a note says otherwise.

1. **Proxy.** Use the proxy already on the server (spec 3), adding one site file and changing nothing else. The repository holds that file as a template for the proxy found at inspection; `infra/prod/proxy/nginx.conf` is written now because nginx is the spec's fallback. If the server runs Caddy or Traefik, Task 7 translates the same rules. Rules: `/api/` goes to `core:4000` and everything else to `dashboard:3000`; `Authorization`, the three `X-Mkt-*` headers, the raw body and DELETE bodies pass through unchanged; request bodies up to 1 MB; no buffering changes to `/api/v1/triggers/`.
2. **Client address behind Cloudflare.** The domain is served through Cloudflare. The proxy takes the client address from `CF-Connecting-IP`, but only for requests from Cloudflare's published address ranges (the ranges file is committed and dated), and sets `X-Forwarded-For` to it. The core runs with `TRUST_PROXY=1`, and Better Auth reads `x-forwarded-for` (`advanced.ipAddress.ipAddressHeaders`). This closes the milestone 2b precondition I7.
3. **Networks.** The three zones of spec 16: `app` (core and dashboard, the only services the proxy reaches), `worker` (core and worker) and `data` (core, worker, postgres, ops), with `worker` and `data` marked `internal: true`. Postgres publishes no port. The worker reaches the core only on `worker` and has no route to the proxy or the internet except the model provider, through a dedicated egress network `worker_egress`.
4. **Limits.** Totals are 2.0 CPU and 4 GB: postgres 0.75 CPU / 1.5 GB; core 0.5 / 1 GB; worker 0.5 / 1 GB; dashboard 0.25 / 512 MB. `ops` is one-shot and runs only when no load test is running. These are proposals until server inspection (A1), as spec 17 says.
5. **Database roles in production.** Postgres starts with a superuser whose password exists only in `postgres.env`. The `ops` image runs the migrations as that superuser, then sets the passwords of `mkt_app`, `mkt_audit_writer`, `mkt_queue` and `mkt_owner_view` from `roles.env` (`alter role … password`). `BOOTSTRAP_DATABASE_URL` is used once, by the owner, then removed from the host (milestone 6 follow-up).
6. **Backups.** The whole database, every schema plus the roles (`pg_dump --format=custom` plus `pg_dumpall --roles-only --no-role-passwords`), encrypted with `age` to a public key. The private key is kept off the server by the owner, so the server cannot read its own backups. The encrypted file is copied off the server with `rclone` to the A4 storage. Runs daily at 02:30 IST from a systemd timer on the host. Keeps 7 daily copies on the server and 30 daily plus 12 monthly off it. `age` and `rclone` are pinned by checksum inside the `ops` image.
7. **Write-once audit store.** An S3-compatible bucket with Object Lock in compliance mode (A5), reached with `@aws-sdk/client-s3` at an exact version at least 30 days old. It implements the existing `ExportStore` port, with object key `audit/<chainKey>/<throughSeq>-<headHash>.jsonl` and retention of 400 days. If the owner prefers a provider without an S3 interface, this task waits.
8. **Worker liveness.** Every call to `POST /worker/approvals/tick` (every 5 minutes) stamps the worker's id and time. `GET /health/worker` answers 503 when no stamp is newer than 15 minutes, and the uptime checker reads it. This covers "missing worker heartbeat" in spec 16. Alerts raised by the worker's own timer cannot report the worker's own death.
9. **Next.js 16.3.8 before go-live.** The critical advisory (milestone 1) should not go to a public address. 16.3.8 must be at least 30 days old at the time of the change (Task 1 checks the release date). Owner to confirm.
10. **Load-test tool.** A Node script with `fetch`, `tools/load/run.mjs`, so no new dependency. It uses the stand-in model with a fixed 2 s answer (`STANDIN_DELAY_MS=2000`), and reads `docker stats` and the n8n canary executions for the figures.
11. **Error tracking.** `@sentry/node` 10.73.0 in the core and the worker, active only when `SENTRY_DSN` is set. `sendDefaultPii: false`, and a `beforeSend` that drops request bodies, cookies, headers other than an allow-list, query strings and the user, and replaces email addresses in messages with `[email]`. The dashboard sends nothing to Sentry in phase 1.

## Review Focus

1. **A request from outside Cloudflare that forges `CF-Connecting-IP` or `X-Forwarded-For`.** Expect the core to see the proxy's peer address, so the limiter cannot be dodged by spoofing (Task 7 smoke check).
2. **A restart of the whole stack while jobs wait.** Expect held and waiting jobs to resume in order, with no duplicate model call and no lost result (Task 5 compose test and Task 9 restore test, "waiting jobs resume").
3. **A backup taken while the core writes audit entries.** Expect the restored chain to verify, because `pg_dump` takes one snapshot (Task 8 test).
4. **A full disk or a failed off-server copy.** Expect the backup to exit non-zero and an alert or failed uptime check, never a silent partial file (Task 8, `backup.sh` fails closed).
5. **A secret placed in an image by a careless `COPY`.** Expect the image scan to fail the build (Task 4 test 39).
