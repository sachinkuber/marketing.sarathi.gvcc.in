# Milestone 6 — Proof Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner signs in, starts the summary agent, sees the item in the inbox, approves it, and sees the run, its cost and its audit entries; the overdue pop-up and banner appear; n8n can call the core through a signed trigger (packages 13, 14 and 15; acceptance tests 33, 34, 37, test 22 in full, and the screen half of test 8).

**Architecture:** The trivial agent is one agent definition (`agents/summary/`), one worker handler that makes one structured model call through the existing `ModelClient` port, and two core result handlers (the summary creates content version 1 and a placeholder-check job in the same run; the check moves the version to awaiting approval). A new access kind, `trigger`, guards a signed endpoint that n8n calls once a day; the core records the heartbeat and runs the daily duties (audit export and verify, exchange rate, nonce clean-up) once per date. A new workspace, `apps/dashboard` (Next.js), is a pure client of the core API on the same origin: it holds no secret, imports no workspace package at run time and reaches no database. The real Anthropic adapter, already written in milestone 4, becomes the production path; the stand-in model stays for tests.

**Tech Stack:** As pinned in spec section 3: Node 24.20.0, TypeScript 5.9.3, Express 5.2.1, zod 4.5.4, PostgreSQL 17.11, pg-boss 12.30.0 behind `@mkt/queue`, `@anthropic-ai/sdk` 0.124.0 (worker only), Next.js 16.3.4 with React 19.2.8, Tailwind CSS 4.3.3, React Hook Form 7.87.0, Nodemailer 9.1.1 (decision 13), Vitest 4.1.11, Playwright 1.63.0. All commands run on the development server through `/opt/mkt-dev/run.sh`.

**Spec:** `docs/specs/2026-10-04-phase-1-foundation.md` sections 8, 10.6, 11, 12, 13, 14, 15, 16, 17 (tests 8, 22, 33, 34, 37), 18 (packages 13 to 15). Also `docs/app-flow/2026-10-04-app-flow.md` sections 3, 4, 5.1, 5.2, 5.6, 5.11, 5.12, 5.15, 5.16, 6, 7.1, 8; `docs/mockups/*.html` and `docs/mockups/assets/app.css`; `docs/database/2026-10-04-database-schema.md` sections 7, 8.3, 9; `docs/progress.md` (milestone 5 follow-ups and deployment notes).

## Global Constraints

- Commands run only on the development server via `/opt/mkt-dev/run.sh` (Node 24.20.0 image, 2 GB, 1.5 CPUs) or the browser variant from Task 14; nothing is installed or run on the laptop. The server address never enters the repository, commits, pull requests or reports.
- Exact versions in every `package.json`, lockfile committed, `npm run check:pins` passes. Any new dependency is named in the decisions below; no other may be added.
- Every core route is declared through `RouteTable.add` with an access kind and a summary. Brand routes live under `/brands/:brandId`; worker routes under `/worker`; trigger routes under `/triggers` (new rule, Task 6).
- All brand data is read and written inside `withBrand`; audit entries are written with the transaction's client (`audit.record(entry, client)`), action names `area.verb`.
- Silence is never approval: no code path in this milestone inserts an `approval`, moves a version to `approved` or creates an `outbox_action` except the existing approve route.
- A result handler runs inside the core's transaction holding the `job_input` lock then the `run` lock (`apps/core/src/jobs/results.ts`); it uses only the given client and does no outside I/O.
- The brief is untrusted input: wrapped in a fixed delimiter, sent with no tools, and the reply is validated by a strict schema before anything is stored (spec 11).
- No secret, address, recipient, brief text or model output in logs; log an error's name and code only (`errorName`).
- Migrations: `0018_*.sql` with `-- Up Migration` / `-- Down Migration`; definer functions follow the 0011/0013/0014 pattern (`security definer`, `set search_path = pg_catalog, app`, owner `mkt_definer`, revoke from public, grant to a named role).
- The dashboard holds no secret and talks only to `/api/...` on its own origin. Inbox, item review, approve, reject, comment, the kill switch, alerts and the overdue pop-up must work at a 390 × 844 viewport (spec 15, app-flow 8).
- Test files live next to what they test (`apps/core/test`, `apps/worker/test`, `apps/dashboard/test`, `apps/dashboard/e2e`, `packages/db/test`). Lint, format check, typecheck, the full suite and the secret scan pass on the development server before the pull request.

## Decisions proposed to the owner

Each is written as the rule the build will follow. Proposed: accept, unless noted.

1. **The dashboard is a client of the core API only, on the same origin.** Pages are client components that call `/api/v1/...` and `/api/auth/...` with the session cookie and the `x-csrf-token` from `GET /api/v1/session`. In development and tests `next.config.ts` rewrites `/api/:path*` to `CORE_INTERNAL_URL`; in production the proxy does the same (package 16). The core's `PUBLIC_ORIGIN` is the dashboard's origin, so the existing origin check holds unchanged. The dashboard imports no workspace package at run time; reply shapes are zod schemas in `apps/dashboard/src/api/schemas.ts`, and a core test parses real replies with them, so the two cannot drift silently.
2. **Browser checks run on the development server in a derived image.** `infra/dev/browser.Dockerfile` is `FROM node:24.20.0@<digest>` plus `npx playwright@1.63.0 install --with-deps chromium`, built once on the server as `mkt-dev-browser:1`. `infra/dev/server-run-browser.sh` runs it with `--memory 3g --cpus 1.5`. The browser suite is `npm run e2e`, separate from `npm run verify`, and runs in CI as a second job. If the owner does not accept a 3 GB container on the shared host, the browser suite is not run, and test 22's screen half, test 8's screen half and the phone checks stay unproven (the API halves and render tests still run).
3. **No new test library for rendering.** Component tests render with `react-dom/server` (`renderToStaticMarkup`) inside Vitest and assert on the markup; interaction is proven only by Playwright. New development dependencies, all for the dashboard build: `@types/react` and `@types/react-dom` (19.2 line, a release at least 30 days old) and `@tailwindcss/postcss` 4.3.3 (the same release as Tailwind). Nothing else.
4. **Next.js advisory.** 16.3.4 has a critical advisory in `next/og`, fixed in 16.3.8 (progress.md, milestone 1). The dashboard never imports `next/og` (an ESLint `no-restricted-imports` rule enforces it), and the pin moves to 16.3.8 as soon as that release is 30 days old; the move is a one-line change plus the full suite. Owner to confirm.
5. **Who may do what on the new routes.** PRD 16.1 has no agent or audit row, and adding a permission key would change the 50-cell comparison test. Reads of agents, runs, model-call review and the audit log use `edit_profile` (platform owner and brand admin, matching app-flow 6). Starting the summary agent, and dead-letter requeue and cancel (unchanged from milestone 4 decision 7), use `see_other_brands` (platform owner only). The member-level status read (kill switch on, shadow mode) uses `member`.
6. **The placeholder check.** A blocking check named `placeholder_length`: passes when the version's `summary` is at most 400 characters and every keyword at most 40. It runs as an `interactive` job in the same run as the summary. Pass: `in_checks` → `awaiting_approval` (which opens the request and notifies approvers, as built in milestone 5). Fail: `in_checks` → `check_failed`; the item is listed in the inbox under "Checks failed" and is not approvable. The core recomputes the rule itself from the stored payload; the worker's answer is only the trigger.
7. **Structured output.** The summary request uses `output_config: { effort: 'low', format: { type: 'json_schema', schema } }` on `messages.create`, `max_tokens` 1024, no tools, no thinking parameter (the model's default). `ModelRequest` gains an optional `outputSchema`. A reply whose `stop_reason` is not `end_turn` (`max_tokens`, `refusal`) is an error the job retries and then dead-letters; it is never stored. Server-side refusal fallbacks are not enabled: one ledger row must stand for one model. If the pinned SDK's types lack `format`, the adapter passes it through a typed cast and the live check (A3) decides; the fallback is an instruction-only JSON request validated the same way.
8. **Daily duties run in the core on n8n's signed daily call; sub-daily duties stay on the worker timer.** n8n calls `POST /triggers/daily` once a day; the core records the heartbeat and runs, each at most once per UTC date: audit export, audit verify (its `onMismatch` wired to `auditMismatchHandler`, closing that milestone 3 and 5 follow-up), the exchange-rate fetch, and nonce clean-up. The model-call sweep, the approvals tick and notification delivery stay on the worker's 5-minute maintenance timer (a daily trigger is too slow for them, and test 41 must not load n8n). This replaces milestone 4 decision 8's "the n8n schedule replaces the timer".
9. **Trigger credential.** `TRIGGER_SECRET` (at least 32 characters, different from the other three secrets; the config test enforces it). In n8n it is a Crypto credential used by the Crypto node's HMAC action (node version 2 takes its secret from a credential), never a workflow field. Refused trigger requests are logged (reason only), not audited, so an unauthenticated caller cannot write to the audit chain; accepted calls are audited as `trigger.received`.
10. **Exchange-rate source.** The European Central Bank's daily euro reference rates (`eurofxref-daily.xml`), USD to INR computed as the cross rate INR/USD, recorded with source `ecb-cross`. The official INR reference (FBIL) has no stable machine-readable feed. Behind an `FxSource` port; tests use a stand-in. Owner to confirm (database schema open point 4).
11. **Owner bootstrap.** `npm run bootstrap --workspace @mkt/core -- --owner-email <address>`, run on the server by the operator: creates Aztek and the test brand if missing, creates the platform owner's account with a random 24-character temporary password printed once to the terminal (never logged or stored elsewhere), and audits `platform.bootstrapped`. Running it again changes nothing. The owner enrols the second factor at first sign-in. Needs A9 for the address.
12. **Enrolment shows the setup key and an `otpauth://` link, no QR image.** A QR library would be a new run-time dependency. The owner may approve one later.
13. **Mail transport.** An SMTP adapter on Nodemailer, active only when `SMTP_URL` and `MAIL_FROM` are set. Nodemailer 9.1.1 has a high advisory (a process-wide DNS cache reuses the TLS server name across transports), fixed in 10.0.14, a new major. Proposed: keep 9.1.1 with exactly one transport per process (which the advisory needs more than one of to bite), and move to 10.x when the owner approves the major change. Owner to decide.
14. **The notification bell is not built.** Spec 15 does not list it; app-flow 4 does. Email and the banner cover phase 1. Follow-up.
15. **Runs with more than one job finish correctly.** The summary run has two jobs, so milestone 4's parked ruling 11 is fixed here: when a job finishes or is cancelled, the run is finalised if no job is dead and none is unfinished and not cancelled.
16. **The core gets an owner-view connection.** `OWNER_VIEW_DATABASE_URL` (role `mkt_owner_view`) for the audit reads and verify, the export reader and `app.record_fx_rate`. Every read of the audit log through it writes an `audit.read` entry (SEC-8, second half).

## Review Focus

1. **A brief or a model reply that should not be stored** — a brief over 2000 characters, with an invisible character, or with text pretending to be instructions; a reply that is not the schema, has four keywords, or carries a zero-width character. Expected: the brief is refused with 400 before any run exists; a bad reply makes the job fail and retry, then dead-letter with a readable reason; no content version is ever created from it. Tests in Tasks 3 and 4.
2. **A signed request whose bytes change in transit** — n8n re-serialises the JSON, a proxy adds a query string or a trailing slash, the clocks differ by 4 and by 6 minutes. Expected: the signature is checked over the raw bytes as received; a changed byte, any query string or a different path is refused; 4 minutes passes, 6 minutes fails. Task 6.
3. **The daily call arrives twice or fails half-way** — n8n retries after a timeout. Expected: each duty runs at most once per UTC date; a failed duty runs again on the retry; a done duty is skipped. Task 7.
4. **The session ends while a person is acting** — approve after the idle timeout, or in a second tab after an edit. Expected: sign-in, then back to the same page; the approve is not lost silently and is refused as stale if the version changed (test 18 through the screen). Tasks 11, 12 and 14.
5. **The kill switch is set while the summary run is in flight, then released while the approvals tick runs.** Expected: the result is held, no version, check job or notification exists; on release the result is applied once and the check job runs; no deadlock between release and tick (milestone 5 follow-up M-2). Task 4.
